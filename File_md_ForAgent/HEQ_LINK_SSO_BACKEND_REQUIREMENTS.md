# 🔐 مواصفات مسارات المصادقة الموحدة لسيرفر HEQ Link
## (HEQ Link SSO Endpoints Contract & Temporary Auth Code Model)

> ### 📌 الوظائف والمهام الأساسية لهذا الملف (File Functions & Scope):
> * **عقد تبادل الرموز الآمن (OAuth2 Code Exchange):** توثيق نموذج بيانات أكواد المصادقة المؤقتة وفترة صلاحيتها.
> * **مسار توليد كود المصادقة (`POST /api/sso/generate-code`):** مواصفات الاستدعاء ومستوى الحماية والاستجابة.
> * **مسار التحقق المباشر بين الخوادم (`POST /api/sso/verify-code`):** بروتوكول التحقق الثنائي عبر `client_secret` وقاعدة الاستخدام لمرة واحدة (One-Time Use).
> * **الفئة المستهدفة:** مهندسو الواجهة الخلفية لخوادم المصادقة الموحدة وأنظمة التكامل.

---

## 1. نموذج تخزين أكواد المصادقة (Auth Codes Model)
نحتاج إلى جدول بسيط أو (Redis) لتخزين الأكواد المؤقتة.
- `code`: سلسلة نصية عشوائية (مثلاً `SSO_...`).
- `userId`: رقم المستخدم في HEQ Link.
- `targetApp`: اسم التطبيق (مثلاً `'werdk'`).
- `expiresAt`: تاريخ الانتهاء (يُفضل أن يكون صالحاً لمدة 1 إلى 2 دقيقة فقط).

## 2. مسار توليد الكود (Endpoint: Generate Code)
- **المسار:** `POST /api/sso/generate-code`
- **الوظيفة:** سيقوم تطبيق HEQ Link (Flutter) باستدعاء هذا المسار عندما يوافق المستخدم على شاشة (هل توافق على المتابعة بواسطة Werdk؟).
- **الحماية:** هذا المسار محمي بـ Access Token الخاص بـ HEQ Link.
- **الاستجابة:** يُرجع الكود المؤقت ليتم تمريره عبر الـ Deep Link إلى Werdk.

## 3. مسار التحقق من الكود (Endpoint: Verify Code)
- **المسار:** `POST /api/sso/verify-code`
- **الوظيفة:** سيقوم سيرفر Werdk باستدعاء هذا المسار خلف الكواليس للتحقق من الكود الذي جلبه تطبيق Werdk.
- **المدخلات:** `code` + مفتاح سري خاص بالاتصال بين السيرفرين (مثلاً `client_secret` متفق عليه).
- **الاستجابة:** 
  - في حال صحة الكود: يتم إرجاع بيانات المستخدم الأساسية `id`, `heq_id`, `email`, `name`, `avatar`.
  - بمجرد قراءة الكود، **يجب حذفه فوراً من قاعدة البيانات** لمنع إعادة استخدامه (One-Time Use).

يرجى إعلامنا بمجرد تجهيز هذه المسارات وتزويدنا بالرابط الأساسي للسيرفر (Base URL) والمفتاح السري (Client Secret) للربط.
